# Agent HTML 输出实践与提示词参考

查阅日期：2026-10-21。

这份文档供用户选择和修改提示词。它覆盖深入解释、研究比较、交互探索和产品界面。它不是新 Skill，也不要求 Agent 每次输出 HTML。

本次阅读了一手文档和公开源码。没有安装这些工具，没有比较模型生成结果，也没有验证它们的输出质量。“可借鉴”和“建议”是本项目的判断，不是质量排名。GitHub `main` 会变化；下文版本和内容只代表查阅时的状态。

## 先保证内容，再选择页面结构

丰富度来自清楚的问题、完整的机制、具体实例和可核查的证据。增加装饰或组件数量不能代替这些内容。

- 先明确读者、要回答的问题，以及读者需要理解或完成的事。
- 先列必须覆盖的事实、推理、条件、反例和未知项，再决定如何展示。
- 根据内容选择文字、图、表格、代码或交互。保留必要的长解释和证据入口。
- 让层级帮助读者阅读。可以折叠细节，但不能隐藏关键限制或删掉推理。
- 根据主题选择布局和视觉语言。不规定卡片、配色、字体、图形风格或章节数量。
- 只有交互能帮助理解或操作时，才增加交互。滑块、筛选、步进和按钮必须产生可见且正确的结果。
- 技术解释可以有高信息密度。产品工作界面应帮助用户操作。营销网站的短文案和首屏规则只在适用时使用。

中英文都采用 ASD-STE100 的表达原则：短句、主动语态、一致术语、明确主体和条件。每句表达一个主要意思。区分事实、假设和不确定性。保留准确的命令、标识符和必要技术细节。不要为了短句删掉必要内容。只有经过标准核验，才声明完全符合 ASD-STE100。仓库的 [AGENTS.md](../AGENTS.md#communication-and-reporting) 保留完整要求。

## 一手来源比较

### Anthropic：frontend-design

[当前源码](https://github.com/anthropics/skills/blob/main/skills/frontend-design/SKILL.md) 从主题、读者和真实内容出发。它要求先形成设计方案，再对照需求检查，最后实现和复核。它不绑定构建工具。

可借鉴：根据具体内容选择视觉方向；用真实材料检查设计；关注界面文案、响应式和可操作性。直接写 HTML 或使用现有项目都可行。

边界：源码也列出审美禁项。若把这些禁项全部变成统一规则，仍可能形成新的固定风格。本项目建议让用户目标和已有设计系统优先，不复制整份指令。

### Anthropic：web-artifacts-builder

[当前源码](https://github.com/anthropics/skills/blob/main/skills/web-artifacts-builder/SKILL.md) 面向复杂交互。它使用 React、TypeScript、Vite、Tailwind 和 shadcn/ui，再通过 Parcel 等工具打包单个 HTML。

可借鉴：复杂状态和多个组件可以先按工程方式开发，再生成便于分享的产物。

边界：构建和依赖成本高于直接 HTML。固定技术栈不是所有解释页面的最小方案。组件库也不能决定内容结构。源码把交付前测试列为可选；本项目建议交付前检查主要交互。此建议不代表已经运行其脚本。

### nicobailon：visual-explainer

[当前源码](https://github.com/nicobailon/visual-explainer/blob/main/plugins/visual-explainer/SKILL.md) 标记为 `0.14.0`。它强调机制图、状态变化和方案差异，并提供公共样式与渲染流程。

可借鉴：让连线说明动作；展示成功和失败路径；用步进展示状态变化；用相同视角比较方案。

边界：当前版要求公共 kit、指定视觉 register 和自己的渲染流程。它限制文字密度，默认采用特定图形风格，并限制额外的浏览器检查方式。本项目建议只借鉴表达方法，不把它作为新的强制输出工具。允许 CDN 库也意味着不能仅凭“单文件”判断离线能力。

### OpenAI：前端设计指导

[Designing delightful frontends with GPT-5.4](https://developers.openai.com/blog/designing-delightful-frontends-with-gpt-5-4) 发布于 2026-03-20。它建议提供真实内容、视觉参考和设计约束，并用浏览器检查布局与交互。文中分别讨论网站和应用界面。

可借鉴：把页面任务写清楚；提供参考材料；沿用设计系统；在多个视口检查实际行为。

边界：营销页的首屏、动效和文案规则不应直接套到技术解释。文章围绕特定模型，文中的能力描述来自厂商。本次没有验证这些质量描述，也不据此推荐固定模型或推理设置。

### 如何组合这些方法

| 页面任务 | 建议方法 | 成本与自由度 | 主要复核内容 |
| --- | --- | --- | --- |
| 深入解释或研究报告 | 直接组织 HTML、文字、SVG 和表格 | 无需构建；内容和结构自由 | 事实覆盖、推理、来源、图文一致 |
| 因果或过程探索 | 在解释页面中增加必要的 JavaScript | 需要定义状态和计算规则 | 参数变化、边界、重置、模型限制 |
| 方案比较 | 同标准比较，加差异图和证据详情 | 无需统一卡片或评分模板 | 标准是否一致、证据是否支持结论 |
| 产品界面 | 沿用项目框架和设计系统 | 成本取决于状态和流程数量 | 真实操作、空白/错误状态、响应式 |
| 需分享的复杂交互产物 | 开发后按需打包单文件 | 增加构建和依赖成本 | 打包后的行为、资源和离线条件 |

以上是本项目的选型建议。单文件、离线可用和无需构建是三个不同条件。内嵌 CSS 和 JavaScript 不会自动消除远程字体、图片、库或数据请求。只有检查实际产物后，才能说明它的运行条件。

## 可复用的原创提示词

以下示例由本项目编写，没有复制来源中的完整提示词。把 `〔占位项〕` 替换为实际信息。根据任务删改要求，不把示例中的内容清单当作固定章节。

### 1. 深入解释或研究

适合系统原理、技术调查、架构说明和研究材料。

```text
为〔读者及其已有知识〕制作一个 HTML 页面，解释〔问题〕。
读者看完后应能〔具体理解或完成的事〕。
资料范围是〔文件、链接、数据及允许检索的范围〕。
产物保存到〔路径〕。

先核对资料，列出必须回答的问题和必须保留的事实。
保留理解结论所需的机制、推理、实例、失败场景和限制。
说明重要结论的证据。在相关内容旁链接准确来源。
区分已验证事实、你的推断、假设和待确认项。
不要编造数字、引文、测试结果或来源。

根据内容设计页面。用图展示关系，用文字解释推理。
图中的连接应说明动作或关系。图表必须与正文一致。
需要详细说明时可以展开细节，但不能省略关键内容。
不要固定卡片、主题、图形风格或章节数量。

使用适合任务的 HTML、CSS 和必要的 JavaScript。
说明外部依赖和运行条件。不要自动打开浏览器或部署页面。
中英文均采用 ASD-STE100 原则。短句不能代替完整解释。
在浏览器检查布局、主要交互和键盘操作。
交付时说明文件位置、已检查事项和未验证事项。
没有浏览器工具时，明确说明没有完成浏览器验证。
```

### 2. 因果与过程交互探索

适合队列、缓存、并发、状态机或参数变化。交互必须对应清楚的规则。

```text
制作 HTML 交互解释，帮助〔读者〕理解〔机制〕。
输入参数是〔参数、单位和有效范围〕。
展示结果是〔输出、状态变化或过程〕。
计算或转换规则来自〔资料或明确给定的规则〕。
文件保存到〔路径〕。

先说明初始条件、规则、假设和模型不能表达的情况。
提供一个可复核的小例子，列出输入和预期结果。
如需合成数据，在页面中明确标注。
不要把演示模型的结果当作真实系统的测量值。

让读者改变参数、逐步查看过程，并能恢复初始状态。
每次操作都应更新相关图形、数值和说明。
提供必要的边界或失败场景。无效输入应给出可执行的提示。
如果变化不能帮助理解，就不增加对应控件或动画。
保留静态文字说明，使读者无需操作也能理解主要机制。

布局和技术选择服从内容，不固定视觉模板。
使用语义化控件，支持键盘，减少动效时仍能理解结果。
中英文均采用 ASD-STE100 原则，并保留单位和技术术语。
验证例子、边界输入、状态更新和重置行为。
在浏览器检查布局与交互。报告实际通过和未测的项目。
```

### 3. 方案比较与决策

适合技术选型、设计审阅和研究结论。没有数据时，不用任意分数制造精确感。

```text
为〔决策者〕制作 HTML，比较〔方案〕。
要支持的决策是〔问题〕。
已知约束是〔必须满足的条件〕。
资料范围是〔文件、链接及允许检索的范围〕。
保存到〔路径〕。

先使用相同标准核对各方案的能力、成本、限制和证据。
区分来源声明、实测结果、你的判断和未知项。
缺少证据时标为未知，不推断为支持，也不推断为不支持。
重要判断在相关位置链接准确来源，并注明适用版本或日期。
不要编造评分。若使用计算，展示输入、规则和单位。

选择能直接看出差异的表达方式。
可以使用对照图、表格、流程差异或可展开证据。
不要把所有方案压进相同卡片而删掉不同的关键条件。
说明推荐适用的条件，以及什么条件变化会改变推荐。
如果加入筛选或权重调整，结果必须实际更新并能重置。

中英文均采用 ASD-STE100 原则。
核对来源与判断的对应关系，检查主要交互和窄屏阅读。
报告研究范围、已验证内容和仍需实测的内容。
```

### 4. 产品网站或工作界面

适合有真实用户任务的页面。原型中的模拟操作应明确标注。

```text
为〔产品及用户〕实现〔页面或主要流程〕。
主要任务是〔用户需要完成的操作〕。
使用〔现有项目、设计系统、品牌资料和真实文案〕。
需要支持的状态和接口是〔状态及接口契约〕。
目标视口和交付位置是〔要求〕。

先检查现有界面和约束，复用已有组件与行为。
没有现有设计系统时，选择与产品和用户有关的视觉方向。
页面结构围绕用户任务组织，不固定营销首屏或卡片布局。
使用真实内容。不要把设计说明或实现术语放进产品文案。

实现主要操作，以及适用的加载、空白、错误和完成状态。
控件必须有实际效果。没有后端时，明确标出模拟数据和行为。
不伪造保存、发布、支付或同步成功。
功能范围以本次要求为准，不增加无关功能。

用语义化结构和清楚的控件标签，支持键盘和可见焦点。
状态不能只靠颜色表达。尊重减少动效设置。
中英文均采用 ASD-STE100 原则，术语和操作名称保持一致。
在浏览器验证主要流程、窄屏、长文本、错误状态和控制台。
记录实际检查的视口与结果。工具不可用时明确说明限制。
交付代码及运行方式，不自动部署或更改真实用户数据。
```

## 交付前复核

这份清单适用于以后使用上述提示词生成的页面。本次只交付研究文档，没有生成或验证 HTML 页面。

| 检查项 | 应有证据 |
| --- | --- |
| 内容完整 | 必须回答的问题都有对应内容；关键推理、限制和反例仍可阅读 |
| 事实可核查 | 来源支持相邻判断；版本和日期清楚；模拟数据有标注 |
| 图文一致 | 连线、状态、数值、单位和结论与正文一致 |
| 交互真实 | 控件改变实际状态；预期结果、失败输入和重置已核对 |
| 布局可读 | 实际检查桌面和窄屏；缩放与长路径不会遮挡内容 |
| 操作可达 | 语义化标签、键盘焦点、图形文字说明和非颜色状态提示可用 |
| 动效适量 | 动效有解释或操作目的；减少动效后仍可使用 |
| 运行条件明确 | 外部资源、启动方式、构建要求和离线限制已说明 |
| 浏览器结果准确 | 说明实际检查的方法、视口、结果和未完成项；不把静态阅读称为实测 |
| 语言准确 | 中英文采用 ASD-STE100 原则；术语一致；不作未经核验的合规声明 |

单页可以只需少量检查。复杂界面需要覆盖主要流程和相关回归。没有新的改动或疑点时，不重复检查同一证据。
